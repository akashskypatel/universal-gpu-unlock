Legacy active multi-NVIDIA execution remains blocked.

## Objective and non-objectives

Make this fork correctly inventory and identify *both installed GPUs*, safely support selection of **one explicitly pinned target** without removing the other card, and—only after separately establishing firmware, ownership and recovery evidence—support an independently validated secure transaction for each card and then, if justified, **sequential per-card** transactions in a single cold boot. Preserve an unmodified stock Windows NVIDIA 617.42 driver and independently measured post-boot correctness.

This is not a claim that dual-card active operation, simultaneous unlock, SEC2 firmware acceptance, CUDA P2P, preservation across GSP resets, warranty coverage, Secure Boot trust, or BitLocker safety is already achieved. Parallel GPU transactions and unattended/persistent DXE execution are out of scope until independent one-card proofs and explicit later authorization.

**Authorization and recovery gates (all currently FALSE):** `CAN_DETACH=false`, `CAN_UNLOCK=false`, `CAN_FLASH=false`, `RECOVERY_VERIFIED=false`. No work item below automatically changes these values. No VBIOS flashing is an implementation goal.

### Non-negotiable stop conditions

- Any unmatched or ambiguous GPU/subsystem/BDF/parent path, changed handle, unexpected GOP/console ownership, or unknown vendor driver implementation → **stop before mutation**.
- Any unproven signed Booter origin, incompatible geometry/signature domain, GSP pair mismatch, absent vendor acceptance evidence, or mismatched PROM hash → **no secure transaction**.
- Any unsupported recovery route, untrusted EFI binary, BitLocker recovery uncertainty or altered Secure Boot configuration → **no automatic/persistent boot**.
- Any failure after first active mutation, nonreturning vendor `Stop`, retained DMA, unexpected FLR or state drift → **no retry, no “stock-safe” assertion**; recovery may require full power-off and independent inspection.
- Passing unit tests, an EFI build, static Ghidra analysis or a checksum match never closes a physical authorization gate.

### Exact current Windows 617.42 research limitations

The known 617.42 analysis establishes driver object/construction and callback code paths **statically**, including a conditional getter returning `outer+0x3E8` when `outer+0x3518==0`; guard writer and upstream state conditions; alternative parent `+0x308` methods classified as **address encoders, not DMA/Booter transfer**; nested Falcon state registration with 71 entries; parent slot values `+0x50→FUN_140179070`, `+0x60→FUN_140178460`, `+0xE0→FUN_140178F50` (indirect forwarding), `+0xE8→FUN_1400061B0` (no-op). The actual signed production Windows Booter image, producer/descriptor, call path to real HS loader, AD102/GA102 runtime class selection and signature acceptance are **not yet proven**. Preserve that gap in this repo; do not treat the older Linux `610.43.03` assets as verified substitutes.

## Practical implementation sequence and test discipline

1. Start with **claims, read-only discovery, and explicit target selection**. These can be implemented and exercised with UEFI mocks without initiating a firmware transaction. Preserve the original single-card behavior where it is correctly constrained; do not delete ownership, error or integrity checking for a green test.
2. Introduce only the **minimum additional state isolation** needed for two recognized targets and independent error handling. Keep one-card-only manual operation as the first physical end state; do not implement speculative concurrent SEC2/DMA engines.
3. Integrate the already reviewed path/ownership predicates and negative host fixtures. Test double-GPU success in **discovery only**; test that active disallowed operations fail when `CAN_DETACH`/`CAN_UNLOCK` are false. Report every real test command, exit code and which checks actually ran.
4. Continue the separate **read-only Windows 617.42 firmware/driver investigation**. Treat firmware source/ABI and recovery as critical blockers, not tasks bypassed by recompilation.
5. After all preceding evidence and **new explicit approval for an individual physical test**, validate one GPU at a time with the other installed, then independently validate the other, then propose sequential same-boot operation. Retain passive-only fallback and restore-Windows-first capability.
6. Package release artifacts only after reproducible build, byte-level hash manifest, PE signature verification, manual pre-boot and per-card Windows bench evidence; distinguish “known compatible with driver 617.42” from “compiled using 610 firmware assets.”

## Definition of done

- Both GPUs are simultaneously *discovered* and exact-card pinned on the MSI B850, with clean read-only output and no dropped or cross-wired adapter.
- Manual targeting either GPU does not alter the non-target GPU in any observed preflight or later **separately authorized** transaction.
- The exact signed and accepted firmware flow for **each GPU under stock Windows 617.42** is established; not inferred from matching strings, masks, older Linux images or a fixed deadline.
- Independent firmware/ownership/PCI/GOP cleanup and recovery evidence exists for each card and then for any sequential dual-card attempt.
- Both GPUs enumerate normally in stock Windows 617.42, each independently meets repeatable matched HMMA issue-rate and numerical controls, and a stock cold boot demonstrably returns to baseline.
- Documentation and v1.7.5-era misleading success assertions are corrected; BitLocker, Secure Boot, anti-cheat, warranty, and 20-second completion guarantees are not presented as certainties.
- Only after verified results may release documentation claim the exact tested configuration, exact inputs, observed performance and known limitations. General “universal” guarantees remain unproven.
